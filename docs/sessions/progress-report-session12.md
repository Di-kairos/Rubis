Блокер сессии 11 («`audio-verify` дал 0/24 с пустой записью, похоже на TCC»)

записано, README получил абзац про рипы с CUE.

Дальше — главное за сессию. Новый тест `CueDecodeTests` (сегмент против полного
декода **по битам**) сразу показал, что дорожка начиналась не со своего кадра, а
со следующей границы блока FLAC. Причина в `SFBFLACDecoder.seekToFrame:`:
libFLAC во время самого seek отдаёт write-колбэком блок с целевым сэмплом, а
декодер обнуляет буфер уже ПОСЛЕ — то есть выбрасывает ровно этот блок. Замеры
легли в модель `landing = (⌊target/bs⌋ + 1)·bs` четыре раза из четырёх; у WAV
через CoreAudio seek точный. Промах — до целого блока: 93 мс при типичных 4096
и 44.1 кГц, у каждой дорожки срезалась бы голова, а хвост залезал бы на
соседнюю.

Апстрим (SFBAudioEngine 0.13.0, последняя) этого не чинил, поэтому лечим у себя:
`CueRegion.decoder(url:)` целится на блок раньше нужного, добирает разницу
декодом и отдаёт уже открытый декодер (`AudioPlayer` открывает только то, что
ещё не открыто). Размер блока читается из STREAMINFO двенадцатью байтами файла;
плавающий блок или не-FLAC — компенсации нет. Модель прибита тестом.

Известно и не тронуто: та же кривизна живёт в обычной перемотке иглой по треку —
там она внутри одного трека и чинится только подменой seek у `AudioPlayer`.
